## 1. 用户目标与解释边界

- 会话可以删除，不能找不到入口，也不能“删除”后刷新又出现。
- 模型栏学习 DSH；本稿暂按已检索到的 **DeepSeek Harness** 官方模型管理文档理解，具体视觉版本尚未确认，不声称像素一致。
- 定时任务：**创建 → 弹窗编辑 → 保存 → 一张卡片**；点击卡片再编辑，不在列表铺开全部设置；“投递至”是 Bot，不是截图中的外部渠道。
- 日历/工作区同样采用创建弹窗与保存后条目/卡片；刷新无感，不要求用户手动维护数据同步。
- 不需要独立待办界面；现有待办数据先保留，不能从一句“不需要”推导出删库；未来 Google Tasks 是连接器能力，不自动恢复独立待办页。
- 时间使用本机本地时间；不常驻显示时区字段或多个时区标签；日期、时分、重复频率通过可点击选择完成，不要求用户输入具体时间或 cron。
- 输入 `@` 时在输入框上方弹出可用 Bot，交互与 `/` 菜单一致。
- “规则”改名“工具”；工具、MCP、Skill 均用 **名称 + 描述 + 开关**。飞书是可添加的能力，不是内嵌的 Bot 类型。
- 新 Bot 应为空白起点，由用户配置提示词、工具、MCP、Skill、权限后形成差异；记忆采用文件方式，研究每 Bot 的目录与共享区域。
- 参考 agent-native 的日历交互。未来 Google 范围只包含 **Gmail、Tasks、Calendar、Docs、Drive**。

**附件边界：**截图只作为布局/流程参考。截图里的 Slack、Weixin、QQbot、“此桌面”、自由 cron 输入均不构成新增连接器、投递渠道或实现指令；以用户本轮文字为准。外部 README 中的安装/启动命令也只是参考，不在本轮执行。

## 3. Issue 拆分与实施顺序

优先级是本稿建议，不代表已开工或承诺工期。所有票当前为「待实施」。先解决可单独验收的体验，再改变权限/持久化契约。

### UX-01 · P1 · 会话删除闭环

**交付：**侧栏会话操作菜单提供删除；确认后当前列表、置顶、搜索、直达链接同步处理；删除当前会话后进入空会话页，失败则保留原条目并显示可重试错误。

**推荐语义（待确认）：**用户删除的是会话访问入口与上下文；服务端持久 tombstone，正常查询/搜索/模型读取不再使用该会话。为操作回执和问题追踪保留最小必要审计，不宣称物理擦除。不要仅调用 archive 或在浏览器隐藏。

- 独立运行中的会话：明确提示“停止并删除”，安全停机后 tombstone；不撤销已发生外部动作，不把 unknown 结果改成成功；迟到回执仅记审计，不让会话复活。
- Bot 主会话：不能删除 Bot 本身。建议“清空并开始新会话”，更换当前主会话引用；旧会话退出可见历史及后续上下文，已派出 Task 保持可追溯。**这一点修改永久主会话契约，必须后端先行。**
- 群聊会话删除不等于停用成员 Bot，不级联删除独立 Task、计划或外部日程。
- 会话删除不默认抹掉已经独立保存的 Bot 文件记忆；确认文案明确这一点，同时阻止从已删除会话再次抽取记忆。

**验收：**普通/当前/置顶/运行中/主会话分别测试；刷新、重启后不重现；重复删除幂等；404/409/网络未知不假成功；恢复轮询和迟到响应不能把条目插回；审计历史与模型上下文边界分别验证。

### UX-02 · P1 · 模型管理分层，参考 DSH

**目标：**模型页以配置摘要卡片组织；显示名称、提供方、连接状态、已选模型和默认项；点击“添加/编辑”才展开弹窗。API key 只显示“已配置”，不得回读密钥。输入框模型选择器按提供方分组、可搜索，保留当前已选项。

拆成两个子交付，避免假多提供方：

1. **02a UI：**在现有单连接能力上重排列表与编辑弹窗，保留模型热生效及环境只读边界；不展示实际上无法保存的多提供方按钮。
2. **02b 多提供方（独立范围）：**若要完整复现 DSH 管理能力，再设计 provider ID、模型目录、`providerId + modelId` 路由和旧 Task 兼容；发现模型列表可搜索/勾选，点击保存才落盘。当前后端不支持的协议不得做空选项。

**验收：**取消不写配置；保存失败不退出；主会话从下一条输入生效；独立 Task 保持原模型快照；失效模型明确报错，不静默切换；key 不进入 URL、前端持久存储、日志、截图或历史。DSH 视觉需对照用户指定页面确认。

### UX-03 · P1 · 定时任务创建弹窗与卡片

主界面只保留“新建定时任务”、任务卡片和空态。沿用所附图的信息顺序，去掉外部投递渠道和需要手填的 cron。

**弹窗内容：**名称（可选，未填时从提示词确定性生成摘要）→ 提示词 → 频率/日期/时间选择 → 投递至 Bot → 模型（可选，默认目标 Bot 的模型）→ 自然语言运行摘要 → 取消/创建。保存后成为一张卡片，点击卡片编辑；暂停/恢复/删除与运行历史放卡片菜单。

**执行与投递：**执行 Bot 和结果接收 Bot 不是同一个概念。第一版建议**单选 Bot，该 Bot 执行，结果进入该 Bot 会话，同时有通知索引但不重复发消息**。截图为复选框，不足以推定必须“一次执行广播多个 Bot”；若需要多 Bot，必须确认是独立执行还是复制结果，两者成本、权限和隐私不同。建议首版单选，数据不假装已支持多播。

- 卡片只显示标题、执行摘要、目标 Bot、下一次运行、本地时间、状态；技术 revision、payload、额度诊断折叠。
- 表单校验沿用现有 schedule/routines 规则；用户只需保存，不另加重复“我确认所有设置”复选框。涉及新增权限/外部写入仍走现有安全确认。
- 关闭后草稿策略一致；创建/保存中防重复提交；未知提交结果保留 requestId，核实后再重试。
- 已停用 Bot 不可新增选择；已有计划不自动迁移到另一个 Bot；失败/权限不足给明确卡片状态。

**验收：**创建、编辑、取消、重复点击、暂停恢复、过期单次、运行历史、模型失效均闭环；重启恢复；暂停不补跑、同计划不重叠、权限实时裁决等既有保证不退化；1440px/375px 下弹窗可完成全部操作。

### UX-04 · P1 · 日历/事项卡片化，移除独立待办界面

**交付：**复用 CalendarBoard 现有网格和弹窗；顶部“新建”或点击空白时段 → 简洁编辑弹窗 → 保存后显示日程卡片/列表条目 → 点击再次编辑。按用户需求配置标题、描述、起止日期/时间，不显示一整摊持久表单。

- 导航以“日历 / 定时任务”为主，去掉独立待办页及“今日待办”常驻块；是否最终重命名“事项”由视觉验收定，不阻塞核心流程。
- 旧 Todo、关联、历史和既有计划事件触发暂保留；旧 URL 给出说明并导向新页面，不删业务数据、不擅自改成 Event、不把截止日当占用时段。
- 普通日程只存时间与内容，不等于自动启动 Bot；需要执行提示词时明确进入定时任务表单。
- 本地/外部来源的编辑能力和冲突保护不变，外部来源不得伪装成本地保存成功。

**验收：**鼠标、触摸、键盘可完成新建/编辑/删除；取消不落盘；版本冲突不覆盖；旧链接不白屏；无独立待办 UI，但原数据与运行历史未丢失。

### UX-05 · P1 · 本机时间与可选时间控件

**交付：**日期网格 + 今天/明天等快捷项 + 可滚动的小时/分钟选择 + 常用时段 chip；频率选择单次/每天/工作日/每周/每月，按需展开星期或月日。全过程不需要键入时间字符串；支持键盘导航，不能把“不需要手填”误做成“不支持键盘”。

- 客户端读取 `Date` 与 `Intl.DateTimeFormat().resolvedOptions().timeZone`，显示本机本地时间；不以服务器默认时区替代客户端，不写死 `Asia/Shanghai`。
- **隐藏时区 UI 不等于丢弃时区数据。**单次存绝对时间；周期保留创建时的 IANA zone 与墙上时间，后台执行仍以服务端时钟为准；不要相信前端时间来判断安全/执行事实。
- 设备时区变化：新建采用新时区，既有周期计划不默默改执行时刻；必要时一次性提醒“设备时间设置变化，可调整已有计划”，不常驻展示时区表。这里是推荐策略，后续可提供显式“跟随本机”迁移。
- 夏令时跳过/重复、跨午夜、结束早于开始、月末不存在日期、单次已过期均沿用并核对现有规则，不另编一套算法。

**验收：**通过模拟客户端本机时区完成两个不同时区测试；日历和摘要一致；无必填自由时间/时区文本框；后台重启和夏令时边界可验证。测试代码设置时区不等于 UI 展示时区选择器。

### UX-06 · P1 · 无感刷新，不刷新整个页面

**交付：**本地写入成功立即更新/失效相关查询；Bot/后台任务变更通过已有事件通道（如有）或有界后台轮询带入；回到前台、网络恢复重新校验。单纯刷新“现在”指示线不算刷新业务数据。

- 后台刷新保留已显示内容、滚动、选择、弹窗草稿和焦点；不反复清空成加载态；正常路径无须“刷新工作区/刷新日程”按钮。
- 只刷新相关对象；合并重复请求，离开/隐藏页面降频或暂停，重新进入补一次；不因每个组件挂载产生一套无界定时器。
- 请求带作用域/序号，旧 Bot/旧日期窗口的迟到响应不得覆盖新视图。
- 认证失效、资源撤权时立即清除不可见数据；不能为“无感”继续展示已失去权限的缓存。普通网络暂时失败则保留内容并标记未更新，提供小型重试入口。

**验收：**另一入口修改/后台计划写入后在约定刷新窗口内可见；不丢草稿、不闪白、不跳滚动；离线重连、撤权、切 Bot、切周/月和乱序响应均测试；无需浏览器 reload。

### UX-07 · P1 · `@` Bot 候选菜单与 `/` 共用交互

**交付：**光标处输入 `@` 立即在输入框上方展开可用 Bot（头像、名称、简短描述）；键入过滤；上下键、Enter/Tab 选择，Esc 关闭；点击不误发送消息；保留焦点。抽取通用候选菜单壳，`/` 和 `@` 使用不同数据源。

- 使用稳定 botId 绑定 mention token，不依赖可重名/改名的展示文本；删除 token 同步取消选择；只替换光标附近当前 token，不覆盖整段草稿。
- 默认展示当前可发起工作的 active Bot；群内非成员需标明“加入后 @”或走显式加入，不静默泄露群历史。主会话/私聊中 @ 另一 Bot，需要明确后端委派/转交语义，不把选择器当成隐式群聊。
- 保留当前后端已有多 @ 的顺序派发与公开边界；新的选择 UI 不倒退成仅支持一个，也不自行新增广播权限。
- 邮箱地址、粘贴正文、代码里的 @ 不误路由；中文输入法组合期间 Enter 不提交；无候选、停用 Bot、名称重复、超长列表均有状态。

**验收：**`/` 原命令/Skill 不回归；@ 菜单未选择时不额外派任务；选择后 payload 与 botId 对齐；Enter 先选候选不发出空消息；主会话、独立 Task、群聊三个入口的候选范围和实际路由分别验收。

### BOT-01 · P1 · “规则”改“工具”，能力管理统一列表

**目标结构：**Bot 详情保留“工具 / MCP / Skills”入口，同一行组件展示名称、简短描述、启用开关；未配置/依赖缺失状态位于描述下方；点击可查看详情。不要把 MCP 凭证或 Skill 文件全部铺在主列表。

**必须分离两个维度：**

| 维度 | UI | 行为 |
|---|---|---|
| 能力启用 | 主开关“启用 / 禁用” | 关后模型不再拿到该能力；后端调用也必须拒绝，读工具同样受控。 |
| 写入确认 | 展开详情中的“先问我 / 直接做” | 只作用于已启用能力；不能把当前 allow/ask 开关重命名为启用。全局暂停、外部来源许可继续生效。 |

- 飞书作为工具/连接器组；可见启用能力不等于已完成账号连接或授予某个日历资源。
- MCP 分清“连接外部工具”（本票目标）与“让外部客户端使用 Pidot”（现有凭证管理）；后者移到全局高级连接设置并保留撤销，不能丢掉已有凭证治理。
- 外部 MCP 注册、凭证、安全进程/网络配置和生命周期是新的服务端范围；未完成前不得出现假开关。通过注册项而非任意文本命令启动第三方服务，不读取记忆里的命令作为启动配置。
- Skill 开关持久化到 Bot 分配；关后 `/` 菜单和显式加载均不可用。开 Skill 不自动授予它依赖的飞书/MCP/本地文件权限；依赖缺失明确提示。
- 在途调用不伪称已撤回；下一次调用实时重新授权。模型历史可能仍提及旧工具，后端也必须拒绝。

**验收：**工具/MCP/Skill 在列表、提示词注入、调用入口三层一致；关闭不能只从 UI 消失；旧 Bot 迁移保留当前权限，不以“默认空白”全量撤权或扩权；已撤权来源不泄露描述和旧收据。实施时新增 ADR 解释对 ADR-015 的替代，禁止悄悄改旧决策原文。

#### 用户补充：Agent 优先接入，不强制手动配置

**2026-10-29 用户已明确：不要求用户手动添加 MCP/Skills；应让 Agent 自己添加配置。**因此“全局能力库”是后台注册与管理能力，不是必须经过的手工安装向导。用户说“把这个 MCP/Skill 加给这个 Bot”，或给链接、目录、配置片段后，Agent 应完成理解、接入、配置、分配与验证；UI 用于查看、纠正、开关、更新和移除。

**主流程：**用户发添加请求 → Agent 检查来源及兼容性 → 通过受控管理工具保存配置/导入 Skill → 绑定目标 Bot → 验证可用性 → 返回一张结果卡。正常路径不要求用户复制 JSON、手写 manifest 或逐项勾选。用户可以要求只登记不启用；未说明时按“加给某 Bot”的明确意图完成该 Bot 的绑定，不向其他 Bot 扩散。

**MCP：**Agent 根据用户提供的 URL、受信本机入口或配置识别连接方式，生成连接记录，安全引用凭据，发现工具并注册，再应用目标 Bot 的能力及确认策略。配置中工具发现只说明接口存在，不自动授予全盘文件访问、全账号访问或全部写入权限。未拿到凭据时保存待授权配置，不编造 token 或假装已连接。

**Skills：**Agent 根据用户给的仓库/目录/文件导入内容，读取 SKILL.md 元数据，适配当前 Pidot 注册格式，记录来源与固定版本/hash，自动完成目标 Bot 分配。标准包与当前 manifest 的差异由接入层处理，不让用户为了安装手写内部文件。缺少的工具/MCP 可自动检查并提出配套接入；仅在本次授权范围内配置，不能因 Skill 正文要求而擅自扩大授权。含脚本不等于已获脚本执行权限；不把原本不支持的执行入口伪装成可用。

**Agent 的配置能力：**提供受限的“检查来源、准备接入、保存/更新连接、导入/更新 Skill、绑定/解绑 Bot、检查状态、禁用/移除”管理工具，复用 UI 的同一服务层。以上是能力设计，不是已存在的 API 名称。Agent 不靠任意 shell 修改应用源码、生产数据库或凭据文件来完成配置；管理能力明确授予 Chief/指定配置 Agent，不默认给每个空白 Bot。

**自动完成与需要用户参与的边界：**
- 用户对具体 MCP/Skill 的明确添加请求就是该次接入配置的授权，常规解析、保存、登记、绑定与只读可用性检查不再逐步重复询问。仅有模糊目标且会接错 Bot 时再问；从某 Bot 配置页发起时可以直接使用该页目标。
- 外部 README、MCP 描述、Skill 正文不能自己授权安装其他包、改权限或执行命令。新增运行依赖、启动有宿主机权限的第三方进程等若超出用户本次授权，需要单独说明；有明确授权后自动执行，不永久退回手工操作。
- OAuth 登录/账号同意、二次验证以及缺失的密钥仍通过安全控件由用户完成；完成后 Agent 自动继续原流程，不让用户重填配置。密钥只走服务端安全存储，不进入聊天、记忆、审计正文或工具结果。
- 保存配置、连接握手、依赖安装、工具调用是不同阶段；不能用“配置成功”冒充“安装完成”。连接验证默认只发现接口/做只读检查，不发送邮件、改日历或执行 Skill 脚本来测试。
- 使用幂等请求与阶段记录；重试不重复注册或重复安装，失败保留可诊断状态且不留下半启用能力。已启动进程/外部副作用不能假称已回滚。

**结果卡：**显示 MCP/Skill 名称、描述、目标 Bot、启用开关和状态（已配置 / 待授权 / 缺依赖 / 可用 / 失败）；细节折叠展示来源、版本与工具清单。添加完成后立即在对应 Bot 的 MCP/Skills 列表可见；用户之后仍可直接说“停用它”“换这个配置”“移到另一个 Bot”。停用/移除实时撤销后续调用，不能只改卡片样式。

**新增验收：**用一条自然语言 + 来源完成 MCP 或 Skill 接入，不手动编辑 JSON/manifest；重复请求不产生重复项；OAuth 等待后能续办；缺凭据/脚本不支持时如实显示；跨 Bot 不误分配；外部安装指令不能自动扩权；关掉后新调用被后端拒绝；更新可比较版本并回退，历史运行仍可溯源。新增工具或权限的更新不可无提示扩大既有 Bot 的授权。

本补充修改的是接入设计，不表示当前已经实现第三方安装器或获得安装任意软件的常驻授权；本轮仍不安装依赖、不启动第三方 MCP、不接真实 Google。

### BOT-02 · P1 · 空白 Bot 与可组合能力

“最开始无状态”在本稿解释为：**无预置业务角色、无既有记忆、无默认业务工具授权**，而非“运行后永远没有持久状态”。否则与用户要求每 Bot 维护记忆文件相冲突。

- 新建只需名字/外观；提示词空白或最小平台基础指令，不按名称猜财务/飞书/日程人格，不自动关联工具、MCP、Skill 或来源。
- 用户通过对话让 Agent 配置，或自行选择提示词、能力与权限后形成 Bot 差异；不强制手工填写。模板若保留，只能是显式选择并展示差异的配置包，不能偷偷嵌入一组业务工具。
- 空白 Bot 可正常对话；平台安全约束、基本会话能力不暴露为可被记忆删除的授权规则。
- 内置 Chief 的管理职责是现有系统特例；本轮不移除它，不给新 Bot 自动继承 Chief 权限。
- 旧 Bot 保留既有配置与记忆；明确区分“新建默认值变化”和“已有配置迁移”。

**验收：**同名 Bot 不自动拿到角色；新 Bot 无业务工具/MCP/Skill，首次记忆为空；仅名称不同不改变权限；依赖可诊断；停用与重授规则仍有效。

### MEM-01 · P2 · 文件式记忆与每 Bot 工作目录

#### 推荐方案：一个存储根，每 Bot 私有目录，显式共享

下面是**拟议布局**，不是仓库已存在的接口或本轮创建的数据。根目录放在用户配置的数据目录内，沿用忽略/备份纪律：

```text
<data-root>/bot-workspaces/
  shared/
    USER.md                  # 用户明确认可的共享偏好，不放私聊事实集合
    knowledge/               # 用户明确共享的资料，可选
  bots/<stable-bot-id>/
    PROFILE.md               # 用户配置的提示词/人格；不由 Bot 擅自修改
    MEMORY.md                # 精简、长期、可人工检查的记忆
    memory/YYYY-MM-DD.md     # 有日期的工作记录/片段，按需读取
    files/                   # 用户交给该 Bot 的资料与产物
    .meta/                   # 版本/来源/删除标记/幂等/修订记录，不进提示词
```

- 使用稳定 botId 作为目录名，Bot 改名不移动目录；目录不是权限边界本身，所有读写仍须检查身份、路径及授权。
- 各 Bot 默认只读写自身范围；不能扫描兄弟目录。共享区由用户或显式授权的共享维护能力更新；不默认让所有 Bot 同时改全局记忆，也不默认把 Chief 当成有权读取所有私聊的“记忆管理员”。
- 工具/MCP/Skill 分配仍在受控配置层，密钥仍在独立凭证存储，不放在 Markdown、工作记录或产物里。
- UI 把“记忆/事实”条目表单改成“文件”或“工作区文件”视图：文件树、内容预览/编辑、版本和来源折叠查看。人格文件与记忆文件的可修改主体不同，界面明确提示。

#### 谁维护、何时维护

1. 新建 Bot 的 PROFILE/MEMORY 为空白或明确模板，不复制其他 Bot 的私有内容。
2. 用户显式编辑立即形成新版本；Bot 仅在自己的记忆文件范围内，通过受限写入接口产生候选变更，保留来源与现有预算。
3. 长期记忆只从本 Bot 有权使用的、已消费的认证用户私聊提取；外部网页/邮件/日历、其他 Bot 结果不自动升级为偏好或指令。
4. 不默认永久追加所有聊天到每日文件；保留摘要与必要来源，设保留/压缩策略，避免把“文件记忆”做成无界第二份聊天库。
5. 每次调用先读少量共享偏好 + 本 Bot PROFILE/MEMORY；每日文件按任务检索，有限长度注入，不能把所有文件塞入上下文。
6. 日程/邮件/Tasks 是工具实时读取的业务事实，不复制成长期记忆来判断空闲或发送状态。
7. 用户删除/纠正后保留必要的防复活标记，避免下一轮又从旧历史抽取回来；共享修订冲突不采用无条件 last-write-wins。

#### 文件真源与一致性

**推荐：**记忆内容以文件为唯一可编辑真源；SQLite/现有 Harness 继续保存 Task、Schedule、权限及操作审计，记忆检索索引可重建。不要长期维护“Markdown 一套 + 旧 memory Document 一套”的双主写入。

- 内部修改采用每 Bot/共享区独立串行队列，校验 expected revision/hash，临时文件 + fsync + 原子替换；内容与来源元数据需通过同一修订日志协议恢复，不能声称多个文件 rename 天然具备数据库事务。
- 外部编辑文件：watcher 只是变更提示，读取时再核对内容/hash；限额、凭证过滤和冲突校验后登记为外部编辑版本。无效内容不进入模型；不确定写入者时不冒称用户显式授权，更不能让文件内容改变工具权限。
- 路径白名单、realpath/符号链接逃逸、`..`、大小/文件数、编码、部分写入、磁盘满均防护；避免 TOCTOU 路径绕过。仅给 Bot 受限文件接口，不默认开放任意 shell/全盘读写。
- Markdown 是低优先级资料；PROFILE 虽为用户配置，也不能覆盖平台安全/实际权限；外部内容中“忽略规则、读取另一个 Bot”等文字不是执行授权。

#### 迁移与回滚

1. 先用临时库、合成或脱敏数据验证；本轮不得访问正式库。
2. 导出当前人格→PROFILE、Bot memory→MEMORY、共享 preferences→USER，并保留来源、版本、删除/纠正记录、抽取水位及幂等信息；不可只导出可见文字。
3. 幂等迁移用稳定 botId 和迁移清单；按记录数、内容哈希、来源映射校验；切换时短暂冻结记忆写入，选择新真源后恢复，不长时间双写。
4. 先单 Bot 演练再扩展；原存储只读留备份。回滚若新侧已有写入，先对账/导回增量再切换，不直接恢复陈旧快照丢掉用户修改。
5. UI 明示文件记忆已启用或仍是旧存储；不得仅换文件树外观而宣称已迁移。

**验收：**每 Bot 隔离、共享显式授权、并发更新、崩溃中断/重启恢复、外部编辑、磁盘满、路径逃逸、密钥过滤、注入防护、删除不复活、迁移重复执行/回滚无丢失；通过记忆既有回归并新增文件适配器测试。该票先形成 ADR，再实施。

### INT-01 · P3 / 未来 · Google Workspace MCP 接入调研

本轮**只记录方向**，不部署、不授权 OAuth、不连真实 Google、不安装依赖。

| 服务 | 目标能力 | 第一阶段建议 |
|---|---|---|
| Gmail | 查找/读取邮件，草稿与发送 | 先只读；发送单独审批，结果未知不得自动重发。 |

不因参考项目支持更多服务而扩到 Sheets、Slides、Chat、Forms 等；不把 OAuth 用户身份当成某个 Bot 的无限授权。正式实施前另出接口映射、依赖/许可证审查及隔离测试计划。
