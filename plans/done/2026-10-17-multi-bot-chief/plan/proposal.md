## 2. 建议下一里程碑：多 Bot 身份、长期会话与 Chief 管理闭环

对应原路线第1–2步，补齐第0步原型中的 Chief + 两个专业 Bot 形态；先不引入跨 Bot 协作和真实外部业务。

**用户可见交付：** 用户可以找 Chief 创建、配置和停用专业 Bot，也能直接进入任一专业 Bot 的长期会话；不同 Bot 的身份、会话、工具与数据权限隔离，刷新和重启后保持；配置变化不会悄悄改变已有 Task 的执行配置。

建议验收规模为 Chief + 两个专业 Bot，复用现有模拟工具和已授权能力，不为了数量假装已经接入邮件/待办服务。

## 4. 下一里程碑的验收底线

- Chief 引导创建专业 Bot 后，用户能直接向它交办工作，不必经过 Chief 转发。
- 两个专业 Bot 的会话、历史、工具产物与权限不会串用；相同用户输入也按目标 Bot 正确路由。
- 新配置对新 Task 生效；已有 Task 不静默换配置、模型或扩权；实时撤权仍拦截下一次执行和恢复。
- Chief 管理权限不等于所有业务工具权限，也不等于所有任务的主管职责。
- Bot 停用与在途任务的行为需在契约评审中明确；不能靠删除审计或丢弃未知副作用“完成”停用。
- 原有 FIFO、显式插入、三选一审批锁卡、新动作新审批、取消终态、Skill、预算和未知结果约束保持。
- 重启后身份、会话关联、固定配置、用量及等待条件保留；恢复不自动批准或扩权。
- 自动测试、lint、build及真实模型网页最小链路验收；真实模型证据与确定性故障夹具分别标注，不沿用旧测试数量冒充新增验收。

## 5. 后续顺序

1. **一层协作闭环（原第3–6步）**：黑板/consult、父子 Task、主管与执行者、子 Agent 阻塞→主管处理→必要时升级用户→原 Task 恢复→主管验收及责任链可视化。群聊 @ 按同一任务与权限契约逐步接入；不是重写已完成的单 Task 恢复。`delegate` 保留为 Chief 的 Bot 创建与管理语义，不用作任务派发名。
