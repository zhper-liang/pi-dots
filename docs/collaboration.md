# 协作规范

> 两个人、一个仓库的最小工作方式。目标不是流程完美，是**任何时候 `main` 都能跑起来**，并且谁也看不懂的改动不会悄悄进去。

## 一、一句话原则

**`main` 是"确认能用"的版本，任何人都不直接往里推。所有改动走分支 → Pull Request → 对方看一眼 → 合并。**

这条守住，其他都好说。

## 二、两个人在哪干活

| 位置 | 用途 |
|---|---|
| GitHub Issues | 任务是什么、谁负责、怎么算做完 |
| 分支 | 这次改动的工作区 |
| Pull Request | 请求合并 + 讨论 + 评审 |
| `main` | 已经验收、随时能跑的版本 |
| `docs/` | 结构、决策、接口（跟代码同一个 PR 一起改） |

任务状态只在 Issues 里管，**不要在 markdown 里再维护一份待办清单**，两边一定会对不上。

## 三、分支命名

```
feat/登录页面       新功能
fix/上传失败        修 bug
docs/更新架构图      只改文档
chore/升级依赖       杂活
```

一个分支只干一件事。干到一半发现要顺手改别的，先做完这件，合并了再开新分支。

## 四、日常循环（两个人一样）

**1. 领任务**
在 Issues 里认领，写清楚：目标、这次包含什么、怎么算做完。别只写"做登录"。

**2. 从最新 main 开分支**

```bash
git switch main
git pull
git switch -c feat/登录页面
```

**3. 写代码，小步提交**

```bash
git status              # 看清自己动了哪些文件
git add 具体文件         # 别用 git add . 一把梭
git commit -m "添加登录表单和空输入提示"
```

**4. 推上去**

```bash
git push -u origin feat/登录页面
```

**5. 开 Pull Request**
网页上点出现的黄色按钮；没有按钮就手动走 `Pull requests → New pull request`，base 选 `main`，compare 选你的分支。

描述写三行，多一个字都别写：

```
做了什么：加了登录表单
怎么验证：npm run dev，空着点提交看有没有提示
Closes #3
```

`Closes #3` 里的数字换成真实 Issue 编号，合并后会自动关掉那个 Issue。

**6. 对方评审**
评审的人**必须真的把项目跑一遍**，不是只看 diff。看完三种结论：

- 通过 → Squash and merge
- 有问题 → 在 PR 里写具体哪一行、期望什么
- 需要大改 → 关掉 PR，重新开分支

**7. 合并后各自收尾**

```bash
git switch main
git pull
git branch -d feat/登录页面
```

## 五、评审看什么

不是看代码写得好不好看，只看四件事：

1. **能跑起来吗**（按 PR 里写的验证步骤走一遍）
2. **改动范围对吗**（说好加登录，结果重构了路由 → 打回）
3. **有没有夹带**（`.env`、密钥、node_modules、无关的格式化）
4. **文档跟上了吗**（改了接口/结构，`docs/` 里对应文件有没有一起改）

## 六、冲突怎么办

两个人改了同一个文件的同一块，就会冲突。

```bash
git switch main
git pull
git switch feat/我的分支
git merge main        # 这里报冲突
```

打开冲突文件，会看到：

```
<<<<<<< HEAD
我的写法
=======
对方的写法
>>>>>>> main
```

**手工把两段合成你想要的结果，然后把 `<<<<<<<`、`=======`、`>>>>>>>` 三行标记全删掉。** 改完：

```bash
git add 冲突文件
git commit
git push
```

规则：**谁的分支谁解决冲突。** 拿不准就停下来问对方"这块你要的最终效果是啥"，不要靠猜，更不要为了让它过去就整段覆盖。

## 七、红线（犯了会很麻烦）

1. **不直接往 `main` 推。**
2. **不提交 `.env`、密钥、token。** 只提交 `.env.example`。已经提交过的密钥，改掉再提交也没用，得去后台重新生成。
3. **不对 `main` 用 `git push --force`。** 会把对方的工作直接抹掉。
4. **不提交 `node_modules/`、`dist/`、数据库文件。** 这些归 `.gitignore` 管。
5. **不动对方正在改的文件。** 动手前微信说一句"我要改 `xxx`"。

## 八、文档纪律

代码和文档放**同一个 PR**。这样评审的人能一起看，Git 也会把文档改动和代码改动记在同一条历史里。

改了什么就改对应的那份，别攒着：

| 你改了什么 | 顺手改哪份文档 |
|---|---|
| 加了功能 / 改了范围 | `plans/` 里对应的计划 |
| 换了技术选型 | `docs/decisions/` 加一条 |
| 改了模块结构、数据流 | `docs/architecture/` |
| 改了接口、字段 | `docs/interfaces/` |
| 改了启动方式、目录 | `README.md` |

## 九、可选：给 main 上把锁

仓库 `Settings → Rules → Rulesets`（老界面叫 `Branches`），给 `main` 加规则：

- 必须通过 Pull Request 才能合并
- 至少 1 人批准

找不到这个入口就先跳过，靠约定也够用。等你们手滑推错一次，自然会想开它。

## 十、每周五分钟

周五花五分钟对一遍：

- 有哪些 PR 挂着没合？
- 有哪些 Issue 其实已经做完了？
- 下周只挑 1–2 件做

**别同时开三个分支。** 两个人、三个未合并分支，就是冲突的温床。
