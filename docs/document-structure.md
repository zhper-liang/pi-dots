# 文档规范

## 分类

```text
README.md                    项目入口：是什么、怎么跑、从哪读
NEXT_STAGE.md                当前状态、进行中计划与授权边界
AGENT.md                     协作与文档规范（本文的上层约定）
docs/                        正式文档：长期有效的项目架构资料
  project-guide.md           项目导读（含架构图与场景说明）
  product/                   产品定义、领域语言、已交付范围
  architecture/              现行架构与数据流
  decisions/                 技术决策：选择、原因、代价、变更条件
  interfaces/                已存在的 HTTP / MCP 接口与数据契约
  engineering/               工程导航与运维手册
plans/                       计划
  active/<topic>/            进行中的计划（含 PLAN、findings、进度）
  done/<日期>-<topic>/       已完成计划：摘要 + 当时的计划正文，冻结
  backlog/                   未授权草案
my-app/                      工程实现；命令与环境变量只在 my-app/README.md
.scratch/<topic>/            本地实施过程与原始证据（不进仓库）
```

## 维护规则

1. `docs/` 只留长期有效的正式文档；计划、findings、临时笔记、逐票流水、会话日志与测试附件不得写入 `docs/`。
2. 产品规则、架构、接口、工程命令各有唯一正文，通过链接引用，不维护重复副本；正式文档要区分"当前支持"与"未来方向"。
3. 技术选择用决策记录（ADR）说明原因和代价；架构图与接口必须能指向当前实现，提案中的概念名不能当已实现接口。
4. 计划完成并验收后从 `plans/active/` 移到 `plans/done/<日期>-<topic>/`，正文冻结不再改状态；长期结论提炼进 `docs/`，后续变更由新计划承接。
5. 逐票票据、会话日志、截图与测试日志留在本地 `.scratch/<topic>/`（已忽略，不进仓库）；历史证据归档在仓库外的备份仓库。
6. 现行入口必须可解析并指向现行规范；改路径时同步更新引用，校验本地链接。
7. 文档整理不修改业务代码、正式库或凭证；没有运行的测试不得声称通过。

## 工作记录

新的多步骤任务在本地 `.scratch/<topic>/` 记录 task_plan / findings / progress，完成后提炼正式结论到 `docs/` 与 `plans/`，原始材料冻结不再更新。候选方向必须单独确认范围才发布，不根据旧计划或修改时间自动接续。
